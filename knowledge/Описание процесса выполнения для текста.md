# Описание процесса выполнения для текста

#### 1. Weaviate БД
- Настроил докер контейнер БД. 
- DEFAULT_VECTORIZER_MODULE: 'none' - отключаем встроенные векторизаторы Weaviate. Мы будем считать вектора сами в Python скрипте (на M1 GPU), чтобы контролировать процесс векторизации без черного ящика.
- [[Weaviate]]

#### 2. Парсинг и векторизация PDF
- Сделал скрипт ingest.py который использует модель BAAI/bge-m3 для создания "плотные" вектора (Dense) и разреженные (Sparse) для гибридного поиска и добавляет в Weaviate
- пока только PDF на pymupdf4llm, потом можно заменить функцию load_and_parse_pdf на Docling
- также захардкожено cpu так как pytorch не хочет работать с MPS, **нужно сделать универсальным для всех платформ**
- Мы используем `CPU` только один раз — при загрузке документов. Когда мы будем **искать** (Inference) или использовать Qwen/DeBERTa для ответов — там мы вернем `MPS`, потому что нагрузка при поиске (обработка одного запроса) в разы меньше, чем при индексации целой книги.
- [[Парсинг PDF]]

#### 3. Зафиксирован retrieval baseline
- Зафиксировал retrieval-first baseline как текущую рабочую опору для следующих этапов проекта.
- Основной пайплайн теперь: `Docling -> section-aware parsing -> hierarchical chunking -> hybrid search -> reranking -> context expansion`.
- В коде вынесены стабильные параметры baseline: `child_chunk_size=320`, `child_chunk_overlap=50`, `parent_chunk_size=1400`, `alpha=0.35`, `recall_top_k=40`, `rerank_top_n=8`, `expand_context_window=1`.
- Основной индекс baseline хранится отдельно от legacy индекса, чтобы можно было честно сравнивать новый и старый retrieval.
- README обновлен под baseline: запуск Weaviate, ingestion, ручной retrieval, benchmark.

#### 4. Улучшен ingestion слой
- Перевел основной PDF parsing с `pymupdf4llm` на локальный `Docling`, `pymupdf4llm` оставил как fallback.
- Добавил разбиение markdown на смысловые секции по заголовкам, чтобы retrieval работал не по плоскому тексту, а по разделам документа.
- Добавил иерархические чанки `parent -> child`, чтобы искать по мелким кускам, но сохранять связь с более широким смысловым блоком.
- Для каждого child chunk начал сохранять metadata: `file_name`, `source_path`, `doc_title`, `section_title`, `heading_path`, `prev_heading`, `block_type`, `parent_id`, `chunk_id`.
- Для retrieval собирается manifest чанков в `.cache/veriflow_rag/baseline_manifest.json`.

#### 5. Улучшен retrieval слой
- Вместо одного retrieval шага сделал многостадийный пайплайн: `hybrid recall -> rerank -> grouping -> context expansion`.
- Hybrid search используется как recall stage, а не как финальный ranking.
- Добавил локальный cross-encoder reranker поверх кандидатов из Weaviate.
- Добавил сборку `evidence blocks`: retrieval теперь возвращает не сырой chunk, а расширенный фрагмент с соседним контекстом и metadata.
- Исправил выбор лучшего child chunk внутри parent блока: теперь берется не первый по позиции, а лучший по score.

#### 6. Добавлен benchmark и сравнение с legacy
- Сохранил legacy baseline как отдельный retrieval режим для сравнения качества.
- Сделал benchmark script, который сравнивает `legacy` и `baseline` на контрольных вопросах по PDF из `data`.
- Benchmark сохраняет markdown отчет и json результат в `reports/`.
- Сейчас benchmark набор маленький, но уже покрывает разные типы запросов: определение, перечисление, факт.
- Для диплома этот набор нужно расширить до `20-50` вопросов и добавить больше типов запросов: сравнение, процедура, числовые факты.

#### 7. Подготовлен универсальный слой структурных сигналов
- Начал замену частных эвристик под конкретные лекции на универсальные сигналы структуры документа.
- Добавил `heading_path` и `block_type`, чтобы retrieval мог учитывать не только текст chunk, но и форму блока.
- Добавил intent-классификацию запроса: `definition`, `enumeration`, `comparison`, `factoid`, `procedure`.
- Добавил структурный boosting по соответствию типа запроса и типа блока.
- Этот слой уже заложен в архитектуру, но его еще нужно дотюнивать на более широком benchmark корпусе, чтобы он стабильно работал на любых доменах.

#### 8. Добавлен constrained answer synthesis слой
- Добавил отдельный synthesis слой поверх retrieval, чтобы система собирала ответ только по найденным `evidence blocks`, без свободной генерации.
- Вынес prompts и `JSON schema` в отдельные versioned файлы внутри репозитория, чтобы их можно было менять и сравнивать независимо от Python-логики.
- Для synthesis выбрал локальную LLM через `LM Studio` по OpenAI-compatible API, с базовой моделью `Qwen3.5-9B`.
- Добавил readiness gate: если retrieval возвращает слишком мало уверенных evidence blocks, synthesis не вызывается и система честно возвращает `insufficient_context=true`.
- Добавил локальную валидацию structured output: проверка JSON, обязательных полей и корректности `evidence_id` в citations.
- Добавил controlled retry для случая, когда локальная модель нарушает schema или возвращает невалидный JSON.

#### 9. Добавлен ручной запуск и benchmark для synthesis
- Сделал CLI для end-to-end прогона: `retrieval -> evidence selection -> synthesis`.
- Добавил synthesis benchmark script, который сохраняет markdown и json-отчеты в `reports/`.
- В benchmark включил не только вопросы по содержимому PDF, но и вопросы вне корпуса, чтобы проверить честный отказ при отсутствии контекста.
- Основные критерии оценки synthesis: groundedness, корректные citations, отсутствие неподтвержденных добавлений и честный `insufficient_context`.

#### 10. Добавлен verification layer поверх retrieval + synthesis
- Поверх уже работающего `retrieval + constrained synthesis` собрал отдельный verification слой, который не заменяет baseline, а перепроверяет уже сгенерированный `draft answer`.
- Verification pipeline сделан линейным, без `LangGraph`: `draft answer -> claim decomposition -> retrieval per claim -> claim verification -> local rewrite`.
- Для verification добавлен отдельный пакет `src/veriflow_rag/verification/` со стабильными модулями:
  - `claims.py` для выделения атомарных claims из draft-ответа;
  - `retrieval.py` для отдельного retrieval по каждому claim;
  - `verify.py` для статусов `supported / partial / unsupported / contradicted`;
  - `rewrite.py` для локального переписывания только проблемных фрагментов;
  - `orchestrator.py` для последовательного orchestration всего процесса.
- Claims специально сделаны не “предложениями вообще”, а отдельно проверяемыми смысловыми кусками, чтобы система могла объяснимо показать, что именно подтверждено, а что требует исправления.
- Для verification добавил отдельные prompts и JSON schema:
  - `claim_decomposition`
  - `claim_verification`
  - `claim_rewrite`
- Верификация использует только claim-specific evidence, а не “весь ответ целиком”, чтобы механизм действительно был похож на агентную перепроверку, а не на повторную общую генерацию.

#### 11. Появился demo UI на Chainlit и разделение ролей модели
- В качестве первого UI для конференционного показа выбрал `Chainlit`, потому что он позволяет быстро показать пошаговый pipeline без отдельного frontend-стека.
- В `src/veriflow_rag/app.py` реализован реальный demo flow:
  1. пользователь задаёт вопрос;
  2. система делает retrieval и строит `draft answer`;
  3. в UI появляется кнопка `Агентная проверка`;
  4. по нажатию запускается sequential verification;
  5. в интерфейсе показываются claims, их статусы, подсветка текста и итоговый переписанный ответ.
- Добавил отдельный UI-слой `src/veriflow_rag/ui/render.py`, который умеет:
  - показывать таблицу claims;
  - подсвечивать проблемные фрагменты разными цветами;
  - рендерить локальные переписывания.
- На этом этапе сознательно отказался от `LangGraph`: для MVP и демонстрации на конференции важнее был прозрачный и контролируемый линейный pipeline, а не полноценный graph runtime.
- Разделил модели по ролям:
  - `draft_model_name` отвечает за первичную генерацию ответа;
  - `verification_model_name` отвечает за decomposition, verification и rewrite.
- Это позволяет подбирать более быстрый draft и более строгий verifier отдельно, а не заставлять одну и ту же модель делать всё одинаково.

#### 12. Усилен synthesis для обзорных вопросов и добавлен demo mode
- Стало ясно, что слишком короткий `draft answer` делает verification визуально слабой: если в ответе 1-2 фразы, то claims почти не из чего извлекать.
- Поэтому в synthesis добавил rule-based `answer depth classifier`:
  - `brief`
  - `standard`
  - `detailed`
- Классификация сделана детерминированной, по паттернам запроса, без отдельного LLM-вызова. Приоритет зафиксирован как `detailed > brief > standard`.
- Для `detailed`-режима:
  - увеличил число evidence blocks;
  - расширил допустимый объём evidence в prompt;
  - добавил content plan, чтобы ответ не схлопывался в одну общую фразу;
  - усилил абзацную структуру, чтобы обзорные вопросы давали несколько independently checkable claims.
- Дополнительно добавил явный `Demo Mode` для конференции:
  - `draft_strategy = conservative | balanced | demo`
  - `verification_sensitivity = conservative | balanced | demo`
- Смысл demo mode:
  - draft делается чуть более обзорным и насыщенным;
  - verifier становится чувствительнее к частичным неточностям;
  - rewrite может сработать чаще, но без подделки ошибок и без использования знаний вне retrieval evidence.
- В `Chainlit` это вынесено в отдельные настройки, чтобы во время демонстрации можно было явно переключать:
  - `Draft model`
  - `Verification model`
  - `Draft strategy`
  - `Verification sensitivity`
- Для конференции зафиксировал отдельный документ со сценарием показа и пресетами demo-режима.

#### 13. Сделан устойчивый structured parsing для локальных моделей LM Studio
- При реальном прогоне локальные модели через LM Studio часто нарушали строгий JSON contract не по смыслу, а по оформлению: например, возвращали результат в fenced-block формате ` ```json ... ``` `.
- Изначально это ломало verification, потому что код ожидал только “чистый” JSON и падал на `json.loads(...)`.
- Чтобы убрать этот класс ошибок, добавил общий tolerant parser `src/veriflow_rag/tools/json_extract.py`.
- Теперь structured parsing:
  - принимает чистый JSON;
  - умеет снимать markdown code fences;
  - умеет вытащить первый валидный JSON object/array из более длинного текста.
- Этот parser подключен и к synthesis, и к verification, потому что для локальных моделей проблема оказалась общей.
- В результате система стала заметно стабильнее при работе через LM Studio native API и перестала разваливаться на “формально правильном, но не идеально оформленном” structured output.

#### 14. Практические выводы по текущему состоянию системы
- На текущем учебном корпусе система уже хорошо показывает:
  - grounded retrieval;
  - constrained synthesis;
  - per-claim verification;
  - honest refusal при отсутствии контекста.
- При этом локальный rewrite срабатывает не всегда, потому что сами PDF относительно согласованные, а retrieval часто поднимает достаточно точный контекст.
- Это означает, что verification layer уже рабочий, но на текущем корпусе он чаще подтверждает draft, чем исправляет его.
- Для сильной конференционной демонстрации нужны три типа сценариев:
  1. `supported-only` пример, где verification подтверждает корректность ответа;
  2. `safe refusal` пример, где система честно говорит `insufficient_context=true`;
  3. `correction-case`, где verifier находит `partial/unsupported` claim и запускает локальный rewrite.
- Если таких correction-cases будет мало на существующих лекциях, стоит добавить небольшой более “конфликтный” корпус: стандарты, регламенты или документы с близкими, но различающимися классификациями и перечислениями.

#### 15. Поверх Chainlit собран отдельный web-интерфейс на Next.js и FastAPI
- Для дальнейшего развития demo стало ясно, что `Chainlit` удобен как быстрый прототип, но ограничивает UX: нет нормальной боковой панели корпуса документов, трудно показать live verification state и локальные анимации переписывания.
- Поэтому поверх существующего Python backend добавил отдельный web-слой:
  - `FastAPI` как API-обёртку над текущими ingestion / retrieval / synthesis / verification сервисами;
  - `Next.js` как основной пользовательский интерфейс `trustRAG`.
- Новый Python web layer вынесен в `src/veriflow_rag/web/` и не смешивается с `Chainlit`-кодом.
- В архитектуре зафиксирован принцип: frontend ничего “RAG-ового” сам не считает, а только обращается к Python backend и получает результат или live events.
- `Chainlit` оставлен в репозитории как legacy/demo fallback, а основной UI теперь развивается отдельно.

#### 16. Переведён документный UX на уровень корпуса, а не отдельных PDF
- На первом web-прототипе у каждого файла были отдельные кнопки `Parse / Vectorize / Reindex`, но это давало неправильную ментальную модель.
- Реальный backend сейчас индексирует не один файл, а весь корпус из `data/`, поэтому интерфейс был переделан на corpus-level UX.
- Итоговая логика теперь такая:
  1. пользователь загружает или удаляет PDF;
  2. изменения отражаются в registry;
  3. затем одной общей кнопкой запускается `Обновить индекс`;
  4. backend пересобирает retrieval-индекс по всем PDF, которые сейчас лежат в `data/`.
- Для этого:
  - упрощён `document_registry`;
  - статусы документов сведены к `uploaded / indexed / stale / error`;
  - file-level ingestion actions убраны из UI;
  - в sidebar оставлены список файлов корпуса, их статусы и `Delete`.
- Такой UX лучше соответствует реальной механике retrieval-базы и не создаёт ложного ожидания “инкрементального индексирования одного PDF”.

#### 17. Добавлен live event protocol через SSE и живая verification timeline
- Для web UI выбрал `SSE`, а не `WebSocket`, потому что текущий pipeline строго последовательный и хорошо ложится на однонаправленный поток событий.
- В `FastAPI` добавил run-manager, который умеет публиковать live events для:
  - corpus reindex;
  - claim verification;
  - локального rewrite.
- Для verification зафиксирован explicit event protocol:
  - `verification_started`
  - `claims_extracted`
  - `claim_started`
  - `claim_supported / partial / unsupported / contradicted`
  - `rewrite_started`
  - `rewrite_span_erasing`
  - `rewrite_span_typing`
  - `rewrite_finished`
  - `verification_completed`
  - `run_error`
- Это позволило в web UI уйти от подхода “проверка рисуется как новые сообщения в чате” и перейти к более правильной модели:
  - draft answer живёт как одно assistant-message;
  - verification обновляет это же сообщение по мере продвижения pipeline;
  - claim statuses, highlights и rewrite появляются live внутри одного блока ответа.

#### 18. Реализован специализированный frontend для trustRAG
- Новый интерфейс собран как отдельное `Next.js` приложение в `frontend/`.
- Выбран стек:
  - `Next.js App Router`
  - `TypeScript`
  - `Tailwind CSS`
  - `TanStack Query`
  - `Motion`
- Интерфейс разбит на три зоны:
  - левая панель документов корпуса;
  - верхняя панель runtime-настроек;
  - центральная chat-панель с draft answer и verification state.
- Для фронтенда сознательно не использовал готовый “общий chat framework”, потому что ключевой UX здесь не обычный диалог, а:
  - claim-level verification;
  - подсветка проблемных spans;
  - локальное переписывание текста внутри уже существующего ответа.
- Дизайн выбран светлый, минималистичный, в research-product стиле:
  - off-white background;
  - белые панели;
  - сдержанная типографика;
  - без перегруженных декоративных элементов, чтобы фокус оставался на reasoning pipeline.

#### 19. Добавлены controlled mismatch demo и воспроизводимый rewrite-case
- После реальных прогонов стало понятно, что на хорошем учебном корпусе система слишком аккуратно отвечает и verification часто подтверждает все claims.
- Для конференции и UI-тестов нужен был гарантированный `rewrite-case`, но без порчи обычного trustworthy-path.
- Поэтому реализовал отдельный controlled mismatch режим:
  - сначала система строит обычный grounded draft;
  - затем, только в demo-конфигурации, локально и детерминированно искажаются 1-2 предложения внутри этого draft;
  - после этого verification получает уже “чуть испорченный” draft и находит problem claims.
- Это сделано не через prompt “ошибайся специально”, а как отдельный post-processing шаг:
  - normal mode не деградирует;
  - поведение стало воспроизводимым;
  - rewrite-case можно стабильно показать на конференции.
- Поддержаны типовые контролируемые искажения:
  - overgeneralization;
  - category mix;
  - unsupported detail;
  - list swap.
- На UI это вынесено в отдельные настройки:
  - `Draft strategy`
  - `Verification sensitivity`
  - `Verification demo`
  - `Fault count`
- Так demo mode стал явным, прозрачным и не маскируется под обычный trustworthy-answering.

#### 20. Усилен synthesis для обзорных вопросов и длинных draft-ответов
- Одной из проблем ранних версий было то, что даже в `detailed` режиме draft часто получался слишком коротким, из-за чего verification выглядела слабой.
- Чтобы исправить это, дополнительно усилил synthesis-слой:
  - для обзорных и demo-запросов расширяется retrieval budget;
  - увеличивается число evidence blocks;
  - усиливается content plan для длинных ответов;
  - при необходимости запускается controlled expansion pass, если первая версия ответа слишком сжата.
- В результате `detailed/demo` draft стал лучше подходить для claim decomposition:
  - больше independently checkable предложений;
  - лучше видны роли verification и rewrite;
  - ответы перестали так часто схлопываться в 1-2 фразы.

#### 21. Доработан live rewrite UX: анимация, tooltips и активный claim
- Для web UI был сделан отдельный `RewriteAnimator`, который не переписывает весь message, а изменяет только problem span внутри текущего ответа.
- Реализованы две отдельные фазы:
  - стирание старого problem-span;
  - печать исправленного варианта.
- Дополнительно доработал подсветку claims:
  - `supported` claims не заливаются зелёным, чтобы интерфейс не перегружался;
  - `partial / unsupported / contradicted` подсвечиваются цветом;
  - при наведении на problem span теперь показывается tooltip с причиной (`reason`) из verification.
- Причина ошибки раньше часто приходила на английском, поэтому prompt verification был уточнён: `reason` и `revised_claim` должны возвращаться на языке claim text. Для русскоязычных вопросов это дало русские tooltips и более понятную таблицу claims.
- Во время последовательной проверки добавил отдельную мягкую серую пульсирующую подсветку активного claim:
  - пользователь видит, какой fragment система проверяет именно сейчас;
  - это особенно полезно для живой демонстрации на конференции.
- После успешного rewrite исправленный fragment перестаёт оставаться красным, чтобы UI отражал уже актуальное состояние текста, а не старый problem span.

#### 22. Добавлены мелкие продуктовые улучшения для стабильного demo-показа
- В web UI добавил сохранение chat history в `localStorage`, чтобы пользовательский поток не терялся от случайного reload.
- Позже появилась и отдельная кнопка `Очистить чат`, чтобы быстро сбрасывать историю между demo-прогонами без перезапуска всей страницы.
- Исправлены frontend-проблемы, которые всплыли только на живом использовании:
  - duplicate key warnings на citations;
  - слишком быстрый переход от `typing` к `verification_completed`, из-за которого rewrite animation не успевала визуально проиграться;
  - сохранение problem highlight после успешного локального переписывания.
- На этом этапе web UI перестал быть просто “обёрткой над Chainlit” и стал самостоятельным демонстрационным интерфейсом для trustRAG:
  - с корпусом документов;
  - с runtime controls;
  - с live verification;
  - с локальным rewritе внутри ответа;
  - с управляемым demo mode под конференционный показ.
