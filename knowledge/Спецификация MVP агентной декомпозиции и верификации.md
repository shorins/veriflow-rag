# Спецификация MVP агентной декомпозиции и верификации

## Цель этапа

На текущем этапе мы **не строим полный agentic graph runtime**, а собираем **демонстрационный MVP**, который соответствует теме выступления:

> Повышение точности Retrieval-Augmented Generation через мультиагентную систему декомпозиции и верификации

Практически это означает:
- пользователь задает вопрос;
- система строит **первичный ответ** на основе retrieval;
- затем пользователь вручную запускает **агентную проверку**;
- система разбивает ответ на семантические claims;
- каждый claim отдельно перепроверяется через retrieval + LLM;
- неточные claims локально переписываются;
- интерфейс наглядно показывает, **что именно было проверено и что именно было исправлено**.

---
## Что считается MVP

MVP считается достигнутым, если система умеет:
- показать **draft answer** после первого retrieval;
- по кнопке `Агентная проверка` запустить verification pipeline;
- разбить ответ на claims;
- присвоить каждому claim один из статусов:
  - `supported`
  - `partial`
  - `unsupported`
  - `contradicted`
- показать evidence для каждого claim;
- выделить проблемные куски в тексте цветом;
- переписать только проблемные куски, а не весь ответ целиком;
- показать итоговый исправленный ответ.

На этом этапе **не обязательны**:
- LangGraph
- trust scoring
- полноценная автоматическая оценка truthfulness
- универсальность на любых доменах
- промышленная устойчивость и масштабирование

---
## Общая архитектурная идея

Система состоит из двух фаз:

### 1. Фаза ответа
- Retrieval получает evidence blocks.
- Draft synthesizer собирает первый grounded answer.
- Этот ответ показывается пользователю как исходный.

### 2. Фаза агентной проверки
- Claim decomposer разбивает draft answer на проверяемые claims.
- Для каждого claim запускается отдельный verification sub-flow:
  - claim retrieval
  - claim verification
  - при необходимости локальный rewrite
- После этого answer rewriter собирает final answer.

То есть в логике системы есть роли:
- `Answer Agent`
- `Claim Decomposer`
- `Claim Verifier`
- `Claim Rewriter`

На текущем этапе все эти роли можно реализовать **на одной локальной модели `qwen/qwen3.5-9b` через разные prompt policy**, а не как разные физические модели.

## Последовательность действий системы

### Шаг 1. Пользователь задает вопрос
В UI пользователь отправляет текстовый вопрос.

### Шаг 2. Retrieval
Система использует уже существующий retrieval baseline:
- `Docling`
- `Weaviate`
- `hybrid recall`
- `cross-encoder reranking`
- `context expansion`

Результат: `EvidenceBlock[]`

### Шаг 3. Draft Answer
Существующий constrained synthesis получает top evidence blocks и строит **первичный ответ**.

Результат:
- `draft_answer`
- `citations`
- `used_evidence_ids`
- `insufficient_context`

Если `insufficient_context=true`, ответ все равно показывается, но кнопка агентной проверки:
- показывать предупреждение, что evidence слабый.

### Шаг 4. Ручной запуск проверки
Рядом с ответом в UI находится кнопка:
- `Агентная проверка` значок робота с круговой стрелкой, типа перепроверка

После нажатия запускается verification pipeline.

### Шаг 5. Claim Decomposition
LLM получает `draft_answer` и возвращает список атомарных claims. Нужно сделать промт, который заставит LLM разбить на атомарные и односмысловые части

Каждый claim должен быть:
- коротким;
- самостоятельным;
- проверяемым отдельно;
- привязанным к конкретному фрагменту исходного текста.

Результат:
- `claim_id`
- `claim_text`
- `source_span`
- `source_sentence_index`

### Шаг 6. Claim Retrieval
Для каждого claim запускается отдельный retrieval запрос.

Запросом является не весь ответ, а **только claim_text**.

Результат:
- `claim_evidence_blocks`

### Шаг 7. Claim Verification
LLM получает:
- исходный claim
- top evidence blocks для claim
- инструкции по статусам

И возвращает:
- `status`
- `reason`
- `used_evidence_ids`
- `rewrite_needed`
- `revised_claim`

### Шаг 8. Локальный Rewrite
Если claim имеет статус:
- `partial`
- `unsupported`
- `contradicted`

то claim считается кандидатом на локальное исправление.

Переписывается **не весь ответ**, а только соответствующий кусок `source_span`.

### Шаг 9. Сборка Final Answer
Answer rewriter берет:
- `draft_answer`
- результаты verification
- список исправленных claims

И собирает:
- `final_answer`
- `applied_rewrites`

## Формат claims и статусов

### Формат claim

```json
{
  "claim_id": "c1",
  "claim_text": "Информационная система реализует три фундаментальных процесса работы с данными: сбор, хранение и обработку.",
  "source_span": "Информационная система реализует три фундаментальных процесса работы с данными: сбор, хранение и обработку.",
  "source_sentence_index": 2
}
```

### Статусы claim

#### `supported`
Evidence прямо подтверждает claim.

#### `partial`
Evidence подтверждает claim не полностью:
- подтверждена только часть утверждения;
- присутствует общая формулировка, но не хватает точных деталей;
- в claim есть уточнение, которого нет в evidence.

#### `unsupported`
В найденном evidence нет достаточного подтверждения claim.

#### `contradicted`
Evidence явно противоречит claim.

---
## Формат результата проверки claim

```json
{
  "claim_id": "c1",
  "claim_text": "...",
  "status": "partial",
  "reason": "Evidence подтверждает общую структуру жизненного цикла, но не подтверждает конкретное перечисление процессов.",
  "used_evidence_ids": ["ev_1", "ev_2"],
  "rewrite_needed": true,
  "revised_claim": "Стандарт ISO/IEC 12207 описывает структуру процессов жизненного цикла и делит их на категории."
}
```

### Значение полей
- `status` — результат проверки.
- `reason` — краткое объяснение, почему claim получил такой статус.
- `used_evidence_ids` — какие evidence реально использовались при проверке.
- `rewrite_needed` — надо ли исправлять claim.
- `revised_claim` — локальная исправленная версия claim.

## Правило минимальной неточности

Нужно избежать ситуации, когда система при малой неточности “переписывает весь ответ”.

Для этого вводится **минимальный порог неточности**.

### Базовое правило
Локальное переписывание включается только если выполнено хотя бы одно из условий:
- есть хотя бы один claim со статусом `contradicted`;
- есть хотя бы один claim со статусом `unsupported`;
- доля claims со статусами `partial/unsupported/contradicted` составляет не меньше `20%` от общего числа claims;
- суммарная длина проблемных `source_span` составляет не меньше `15%` длины ответа.

### Следствие
- если claim слегка неточен, но в целом ответ хороший, система только подсвечивает это в UI и показывает замечание;
- если ошибка существенная, переписывается только соответствующий фрагмент;
- полный пересбор всего ответа на этом этапе **не делается**.

### Приоритеты переписывания
- `contradicted` → всегда переписывать;
- `unsupported` → переписывать;
- `partial` → переписывать только если ошибка влияет на смысл;
- `supported` → не переписывать.

## UI-концепция в Chainlit

## Основной сценарий

### 1. Сообщение пользователя
Пользователь задает вопрос.

### 2. Показ первичного ответа
Система показывает:
- `Draft Answer`
- citations
- справа или ниже кнопку `Агентная проверка`

### 3. Запуск проверки
После нажатия кнопки UI начинает пошагово показывать:
- `Извлечение claims...`
- `Проверка claim 1...`
- `Проверка claim 2...`
- `Переписывание проблемных фрагментов...`

### 4. Визуальная подсветка текста
В самом тексте ответа claims выделяются цветом:
- зеленый — `supported`
- желтый — `partial`
- красный — `unsupported`
- бордовый/красный с зачеркиванием — `contradicted`

### 5. Переписывание фрагментов
После завершения проверки UI должен показать:
- исходный problematic span
- новый rewritten span
- обновленный итоговый ответ

### 6. Финальный вид
Пользователь видит:
- `Draft Answer`
- `Verification Table`
- `Highlighted Answer`
- `Final Corrected Answer`

## Как это ложится на Chainlit

На текущем этапе `Chainlit` подходит как лучший интерфейсный слой, потому что позволяет:
- быстро поднять chat UI;
- показывать шаги выполнения;
- обновлять сообщения по ходу пайплайна;
- рендерить markdown/HTML для цветной подсветки;
- показывать кнопки/действия.

### Что использовать в Chainlit
- одно основное сообщение для `Draft Answer`
- action/button `Агентная проверка`
- отдельный live step stream для progress
- HTML/Markdown блок для цветной версии ответа
- отдельный блок для `Final Answer`

### Как показать “живое переписывание”
На первом этапе не нужен сложный editor-like UI.

Достаточно такой анимации:
- показать draft answer
- обновить текст с подсветкой статусов
- затем заменить проблемный span на исправленный
- затем показать final answer как новую версию

То есть фактически это последовательные апдейты UI, а не полноценный rich text editor.

## Технический backend-подход

На этом этапе backend должен быть **простым и линейным**, без LangGraph.

### Оркестрация
Используем обычный Python orchestration pipeline:
- `run_retrieval()`
- `generate_draft_answer()`
- `extract_claims()`
- `verify_claim()`
- `rewrite_claims()`
- `assemble_final_answer()`

### Почему пока без LangGraph
- LangGraph добавит лишнюю сложность;
- текущий pipeline линейный и хорошо выражается обычным Python-кодом;
- для MVP и конференции важнее работающий сценарий и наглядность, чем graph runtime.

LangGraph можно добавить потом, когда система стабилизируется.

## Prompt policy по ролям

### 1. Draft synthesizer
- использовать только evidence;
- не использовать внешние знания;
- вернуть grounded answer + citations.

### 2. Claim decomposer
- разбивать ответ на атомарные claims;
- не терять смысл;
- возвращать claims в том порядке, в котором они идут в тексте;
- обязательно сохранять `source_span`.

### 3. Claim verifier
- проверять один claim за раз;
- использовать только claim-evidence;
- возвращать один из фиксированных статусов;
- объяснять причину;
- не переписывать claim, если он `supported`.

### 4. Claim rewriter
- переписывать только проблемный claim;
- сохранять стиль исходного ответа;
- не добавлять новых неподтвержденных деталей;
- делать текст вставляемым обратно в draft answer.

## Критерии качества для текущего этапа

На текущем этапе система считается достаточно хорошей для demo, если:
- definition/factoid кейсы работают стабильно;
- на части сложных кейсов verification показывает проблемные claims;
- система не галлюцинирует при перепроверке;
- проблемные claims исправляются локально;
- UI наглядно объясняет, что именно произошло;
- пользователь видит, что это **не просто генерация**, а именно **декомпозиция и перепроверка**.

---
## Что не нужно делать сейчас

- Не внедрять trust scoring.
- Не пытаться построить полноценную универсальную NLI-систему.
- Не добавлять LangGraph только ради “мультиагентности”.
- Не усложнять UI до полноценного rich text diff editor.
- Не пытаться делать полную автоматическую правку всего ответа.

---
## Рекомендуемая формулировка текущей версии проекта

Текущую систему на этом этапе можно формулировать так:

> Локальный Retrieval-Augmented Generation pipeline с агентной декомпозицией ответа на claims, повторным retrieval для каждого claim, LLM-верификацией и локальным переписыванием неподтвержденных смысловых фрагментов.

Это достаточно точно, сильно звучит и соответствует реальной архитектуре текущего MVP.
