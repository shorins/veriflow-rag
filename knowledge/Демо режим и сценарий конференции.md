# Демо режим и сценарий конференции

## Цель demo mode

Demo mode нужен для конференционного показа агентной верификации без подделки ошибок.

Система в этом режиме:
- строит более обзорный и насыщенный `draft answer`;
- делает verification более чувствительным к частичным неточностям;
- повышает шанс локального `rewrite`, который можно показать в интерфейсе;
- при этом остаётся grounded и использует только retrieval evidence.

Demo mode не предназначен как production-режим по умолчанию. Это отдельный явно включаемый режим для наглядной демонстрации пайплайна `draft -> claims -> verification -> local rewrite`.

## Настройки для conference demo

Рекомендуемый preset в `Chainlit`:

- `Draft model`: `qwen2.5-vl-3b-instruct`
- `Verification model`: `qwen2.5-vl-7b-instruct`
- `Draft strategy`: `demo`
- `Verification sensitivity`: `demo`

Если `7B` слишком медленная:

- `Draft model`: `qwen2.5-vl-3b-instruct`
- `Verification model`: `qwen2.5-vl-3b-instruct`
- `Draft strategy`: `demo`
- `Verification sensitivity`: `demo`

Ограничение для сцены:

- запускать только **один вопрос за раз**;
- не использовать batch benchmark;
- ждать завершения draft до запуска verification;
- не нажимать повторно кнопку `Агентная проверка`, пока идёт текущая проверка.

## Основной демонстрационный сценарий

### Основной запрос

`В чем различие жизненного цикла информационной системы и жизненного цикла программного обеспечения?`

### Почему именно этот вопрос

- comparison-вопрос провоцирует draft на обобщение;
- verifier может поймать неточность в противопоставлении;
- локальный rewrite выглядит естественно и понятно для аудитории.

### Что показывать

1. Задать вопрос.
2. Дождаться `Draft Answer`.
3. Показать metadata:
   - `draft_model`
   - `verification_model`
   - `draft_strategy=demo`
   - `verification_sensitivity=demo`
   - `answer_depth`
4. Нажать `Агентная проверка`.
5. Показать:
   - извлечение claims;
   - цветную подсветку ответа;
   - таблицу claims со статусами;
   - `Final Answer` после локального rewrite.

### Что говорить

- “Сначала система строит черновой ответ на основе retrieval.”
- “Затем она разбивает этот ответ на проверяемые смысловые утверждения.”
- “Для каждого утверждения запускается отдельный retrieval и отдельная проверка.”
- “Если утверждение сформулировано слишком широко или неточно, система переписывает только проблемный фрагмент, а не весь ответ целиком.”

## Резервные вопросы

### Резервный вопрос 1

`Расскажи подробно про жизненный цикл информационной системы, какие этапы обязательны, а какие вспомогательные?`

Ожидаемый эффект:

- draft может смешать этапы, процессы и вспомогательные активности;
- verifier может отметить часть claims как `partial`.

### Резервный вопрос 2

`Какие основные процессы жизненного цикла перечислены в ISO/IEC 12207?`

Использовать только как резерв:

- этот вопрос иногда проходит слишком гладко;
- он лучше подходит как дополнительный сценарий после основного comparison-case.

### Safe refusal demo

`Какая столица Франции?`

Что показывать:

- `insufficient_context = true`;
- система честно отказывается отвечать по нерелевантному корпусу.

Это хороший завершающий пример trustworthy-поведения.

## Что делать, если rewrite не сработал

Если на основном вопросе verification пометил всё как `supported`:

1. Не паниковать и не перезапускать batch.
2. Переключиться на резервный comparison/overview вопрос.
3. Если `7B` verifier не активен, переключить `Verification model` на `qwen2.5-vl-7b-instruct`.
4. Оставить `Draft strategy=demo` и `Verification sensitivity=demo`.

Если даже после этого rewrite не произошёл:

- показать сам verification pipeline;
- акцент сделать на том, что система умеет:
  - извлекать claims,
  - привязывать их к evidence,
  - честно различать `supported` и `insufficient_context`.

То есть rewrite — сильный эффект, но не единственная демонстрационная ценность.

## Что не обещать аудитории

Не стоит формулировать систему как:

- “полностью надёжный универсальный verifier истины”;
- “готовая мультиагентная платформа для любых доменов”;
- “production-grade fact-checking система”.

Корректная формулировка:

- “локальный MVP агентной декомпозиции и верификации поверх RAG”;
- “система, которая умеет извлекать claims, перепроверять их по retrieval evidence и локально исправлять проблемные фрагменты ответа”;
- “демонстрация архитектурного подхода к повышению точности RAG”.

## Последовательность показа на конференции

1. Открыть `Chainlit`.
2. Показать выбранные настройки demo mode.
3. Запустить основной вопрос.
4. Показать `Draft Answer`.
5. Показать citations.
6. Запустить `Агентная проверка`.
7. Дождаться таблицы claims и подсветки.
8. Показать `Final Answer`.
9. При наличии времени показать `Safe refusal demo`.

## Практическая рекомендация перед выступлением

Перед конференцией прогнать вручную и записать:

- какой основной вопрос сработал лучше всего;
- сколько времени занял `draft`;
- сколько времени заняла `verification`;
- произошёл ли `rewrite`;
- какой резервный вопрос использовать, если основной сценарий на сцене окажется “слишком зелёным”.

Для подготовки выступления использовать только последовательные прогоны, без батчей.
